# Промпт: BoundaryGuard — статический анализатор архитектурных правил Go

Ты — самостоятельный Go backend-разработчик уровня middle, умеющий работать с AST, go/types и go/analysis. Реализуй законченный CLI-инструмент BoundaryGuard для проверки архитектурных границ и запрещенных обращений к символам в Go-проектах.

Цель — полезный инструмент для портфолио с проверяемой семантикой, точной диагностикой и тестами ложных срабатываний. Работай с файлами, терминалом и Git. Результат должен запускаться на реальных Go-модулях и в CI.

## Порядок работы и качество

- Прочитай AGENTS.md и аналогичные инструкции, осмотри каталог, git status и инструменты. Сохрани чужие изменения. В существующем репозитории работай в отдельной ветке; пустой проект инициализируй как самостоятельный репозиторий.
- Дай короткий план и приступай к работе. Не останавливайся на плане и не жди подтверждения каждого этапа. Рутинные технические решения принимай самостоятельно и объясняй в документации.
- Выбирай поддерживаемые стабильные версии по официальной документации и фиксируй их. Не используй плавающие latest-теги. Исторические даты Git не являются заявлением о времени появления выбранных версий: фактическое окружение документируется отдельно.
- Качество уровня middle: небольшие понятные пакеты, явные зависимости, осмысленные интерфейсы, корректная обработка ошибок, тесты существенных свойств. Не создавай универсальный framework и абстракции без потребителя.
- Каждый этап завершается рабочим изменением с тестами и содержательным коммитом. Не создавай весь проект заранее с последующим искусственным разрезанием на историю.
- Проверки запускай сам. Невыполненные проверки обозначай NOT RUN с причиной и командами воспроизведения. Не выдумывай нагрузочные результаты, найденные баги, внешних пользователей и коммерческий опыт.
- Если инструмент недоступен, продолжай независимую работу и точно обозначь препятствие. Не публикуй репозиторий, не выполняй push и не меняй глобальные настройки Git автоматически.
- Регулярно кратко сообщай, что реализовано, чем проверено и какой вопрос решается дальше. Доведи работу до критериев приемки в пределах доступных инструментов.


## Масштаб и структура

- Go, стандартные go/ast и go/types, golang.org/x/tools/go/analysis, analysistest, официальный analysis driver. JSON-конфигурация разбирается стандартной библиотекой.
- Базовый CLI на singlechecker или multichecker. Не пиши собственный type checker и загрузчик модулей без необходимости. Возможности и коды завершения выбранного драйвера проверь по его документации и subprocess-тестами.
- Структура: cmd/boundaryguard, внутренние пакеты configuration, analyzers и facts по фактической ответственности, testdata, examples, docs, scripts.
- Никаких HTTP-сервера, PostgreSQL, frontend, Docker-инфраструктуры для запуска CLI и обязательных облачных сервисов.
- Первая версия проверяет известный исходный код выбранного модуля и его зависимости в рамках описанной семантики. Не обещай доказательства отсутствия всех архитектурных или security-проблем.

## Конфигурация

Файл boundaryguard.json содержит version, layers, dependency_rules и forbidden_symbols. Формат опиши в docs/configuration.md и приложи проверяемый пример.

- Слои определяются каноническими import paths: точное совпадение либо префикс с суффиксом /..., включающий сам корневой пакет и его подпакеты. Произвольный regex/glob в первую версию не входит.
- Например: domain соответствует example.com/shop/internal/domain/...; storage — example.com/shop/internal/storage/...; transport — example.com/shop/internal/transport/... .
- Правило зависимости задает id, from_layer, to_layer и direct/transitive. Например domain не зависит от storage, в том числе через shared.
- Запрет символа задает id, область пакетов и полное имя package-path.Symbol. В первой версии поддержи package-level функции и переменные, например net/http.Get, net/http.DefaultClient, log.Fatal.
- Неизвестные JSON-поля, повторяющиеся идентификаторы правил, ссылки на отсутствующие слои, неподдерживаемые шаблоны и неоднозначное сопоставление слоев считаются ошибками конфигурации.
- Конфигурация передается явным флагом, например -config. Путь разрешается относительно рабочего каталога запуска и превращается в абсолютный один раз, а не отдельно в каждой анализируемой зависимости.
- Проверяй валидность конфигурации до запуска основной работы. Отсутствие или ошибка конфигурации не должны давать успешный отчет «нарушений нет».
- Создавай анализаторы через фабрику с неизменяемой конфигурацией, пригодной для независимых тестов. Избегай глобальных изменяемых map и незащищенного общего состояния.

## BG001: запрещенная прямая зависимость

Находи прямые импорты пакетов из запрещенного слоя:
- Проверяй canonical import path, а не локальное имя alias.
- Учитывай обычные, переименованные, blank и dot imports.
- Позиция диагностики — соответствующий import spec. Укажи ID правила, исходный пакет и запрещенный пакет.
- Нельзя считать package path простым префиксом строки без границы сегмента: /domain и /domainish — разные пути.
- Разрешенные направления и неклассифицированные пакеты должны иметь явную семантику.

## BG002: запрещенные обращения к символам

Находи ссылки на заданные функции и переменные по types.Object и TypesInfo:
- Переименование import, dot import и локальная переменная с тем же именем не должны ломать проверку.
- Не путай одинаково названные символы разных пакетов, локальные функции и поля структур с package-level объектами.
- Диагностируй ссылку на запрещенный символ, включая сохранение функции в переменную: get := http.Get. Не ограничивайся только CallExpr.
- Для http.DefaultClient диагностируй саму ссылку на переменную, не пытайся угадывать любой объект типа http.Client.
- Одна ссылка дает одну диагностику, без повторов на родительском selector и вложенном identifier.
- Применяй правило только к настроенной области пакетов.
- Ограничение: инструмент проверяет ссылки, присутствующие в анализируемом коде. Он не доказывает отсутствие вызовов через reflection, плагины и произвольные внешние обертки. Не добавляй whole-program SSA ради неподтвержденного расширения масштаба.

## BG003: запрещенная транзитивная зависимость

Находи путь вида domain → shared → storage, если настройка запрещает domain зависеть от storage транзитивно.

- Используй package facts go/analysis, передаваемые от зависимостей к импортирующему пакету, либо обоснуй другой совместимый модульный подход.
- Учитывай промежуточные неклассифицированные пакеты анализируемого модуля; они не должны превращаться в лазейку.
- Не обрезай обход на пакете с разрешенным прямым импортом: конечная запрещенная зависимость все равно должна обнаруживаться.
- Для каждого нарушения показывай одну воспроизводимую цепочку-свидетель. Выбирай кратчайшую, при равной длине — лексикографически стабильную.
- Не перечисляй все возможные пути. Храни ограниченный набор свидетельств по целевым слоям, чтобы не получить экспоненциальный объем facts.
- Facts должны иметь детерминированное сериализуемое представление, версию схемы и fingerprint конфигурации. После экспорта их нельзя изменять. Несоответствие схемы или политики не должно незаметно превращаться в отсутствие нарушений.
- Не полагайся на наличие facts стандартной библиотеки у любого драйвера. Гарантию транзитивного анализа ограничь пакетами анализируемого модуля; внешние пакеты могут быть явно классифицированными конечными целями прямых ребер. Не объявляй внешние скрытые зависимости полностью исследованными.
- Если прямая зависимость уже объясняет то же правило, не дублируй ее отдельной транзитивной диагностикой.
- Позиция транзитивного нарушения — импорт первого шага пути в проверяемом пакете. Сообщение содержит полный путь и ID правила.

## Диагностика и интеграция

- Каждое сообщение имеет стабильный код BG001/BG002/BG003 и ID конфигурационного правила, файл, строку и колонку.
- Поддержи стандартный текстовый вывод и JSON выбранного analysis driver. Формат и особенности стабильности опиши; не обещай собственный плоский JSON, если используется формат драйвера.
- Документируй и проверь коды завершения: чистый анализ, найденные нарушения, ошибка загрузки/компиляции и неверные параметры не должны случайно считаться одинаковым успехом.
- Проверь запуск по шаблонам пакетов ./..., build tags, generated files, внутренним и внешним тестовым пакетам и go.mod с replace. Документируй, какой набор исходников анализируется.
- По умолчанию учитывай generated files. Не вырезай их импорты из графа незаметно. Любые исключения требуют явной семантики и тестов; механизм подавлений не обязателен для первой версии.
- Результат для одинаковых исходников и конфигурации должен быть детерминированным с учетом особенностей выбранного драйвера. Сортируй собственные коллекции и пути свидетельств.
- Для архитектурных нарушений не выдавай случайные автоисправления. Удаление импорта или замена вызова без понимания бизнес-семантики не является корректным SuggestedFix. Вместо этого объясняй направление исправления в документации.
- Предусмотри GitHub Actions для запуска инструмента на демонстрационном модуле. Если добавляешь go vet -vettool, проверь совместимость выбранного main и протокола реальной командой; неподтвержденную поддержку не заявляй.

## Тесты

Используй analysistest с // want ожиданиями для диагностик и facts, unit-тесты конфигурации, golden-проверки стабильных сообщений и subprocess-тесты реального CLI.

Обязательны:
1. Нарушение каждого правила и чистый соседний пример.
2. Import alias, blank import, dot import и похожие package paths.
3. Локальный http, локальный Get и символ с тем же именем в другом пакете — без ложного срабатывания.
4. Прямая ссылка на функцию, вызов, присваивание функции переменной и ссылка на DefaultClient.
5. Прямой и транзитивный путь, несколько путей одинаковой длины, разрешенное направление и неклассифицированный промежуточный пакет.
6. Отсутствие дубликатов одной диагностики; детерминированный выбор цепочки.
7. Два независимых запуска с разными конфигурациями не загрязняют результаты друг друга; fingerprint facts учитывается.
8. Ошибка JSON, неизвестное поле, перекрывающиеся слои и неверный путь файла.
9. Generated files, build tags, test variants и replace в тестовом модуле.
10. Ошибка компиляции и недоступная зависимость не превращаются в зеленый CI.
11. Анализ корректного Go-кода не меняет исходники.
12. Параллельные проверки проходят применимый go test -race без найденных гонок.

Дополнительно fuzz-тестируй чистую функцию разбора/валидации конфигурации: нет panic, результат либо валидная конфигурация, либо контролируемая ошибка. Для небольших случайных DAG сравни вычисленные зависимости с простым эталонным BFS; публикуй seed при неудаче. Не пытайся компилировать графы с циклическими импортами как корректные Go-пакеты.

Тестовые fixtures с ожидаемыми нарушениями изолируй так, чтобы обычный go test ./... и линтер не считали их ошибками самого продукта. Каждый анализатор и правило должны иметь негативные примеры, а не только демонстрации срабатывания.

## Демонстрация, производительность и приемка

Подготовь компилируемый examples/shop с domain, application, storage, transport и shared. В отдельном нарушающем варианте покажи:
- domain напрямую импортирует storage;
- domain получает storage через shared;
- transport обращается к запрещенному символу стандартной библиотеки.

Команда make demo показывает ожидаемые диагностики и не путает ожидаемый ненулевой код анализатора с падением оболочки. Рядом должен быть исправленный вариант с чистым результатом.

Сделай параметризованный генератор синтетического модуля и сравни небольшие, средние и более крупные графы в пределах ресурсов окружения. Разделяй стоимость загрузки/проверки Go-пакетов и собственно анализатора; явно указывай прогретый или холодный кеш. Измеряй wall time, CPU и память, сохраняй версии, конфигурацию, размер графа и сырые результаты. Не заявляй ускорение без сопоставимого эксперимента.

Если доступны исходники реального durableq или сенсорного навигатора, добавь отдельный воспроизводимый прогон без изменения этих репозиториев. При их отсутствии используй examples и обозначь это; не приписывай инструменту найденные баги или внешних пользователей.

Репозиторий содержит README, docs/configuration.md, docs/rules.md, docs/architecture.md, 2–3 ADR, docs/benchmarks.md, docs/demo.md, testdata, examples, Makefile и CI. Объясни пределы анализа, поддержку версий и выбор модульных facts вместо полного исследования программы.

Команды: make build, make test, make lint, make demo, make bench. Документируй установку через go install с фактическим module path; не используй выдуманный GitHub URL. Сам продукт должен проходить собственную подходящую конфигурацию; исключения объясни.

Официальные опорные материалы: https://pkg.go.dev/golang.org/x/tools/go/analysis ; https://pkg.go.dev/golang.org/x/tools/go/analysis/analysistest ; https://pkg.go.dev/golang.org/x/tools/go/analysis/singlechecker .

## Коммиты и календарь

Количество коммитов свободное: выбирай его по законченным изменениям. Код, относящиеся к нему тесты и необходимые изменения документации должны попадать в соответствующий этап. Дополнительные исправляющие коммиты разрешены. Не делай пустых коммитов ради количества и не применяй squash.

Параметры дат для этой версии промпта:
- COMMIT_DATE_MODE = historical
- COMMIT_DATE_START = 2026-07-10
- COMMIT_DATE_END = 2026-10-14
- COMMIT_TIMEZONE = Europe/Moscow, UTC+03:00

Диапазон можно изменить перед запуском. При режиме actual используй фактические даты и пропусти генерацию календаря. При historical соблюдай следующие правила:

1. Это заданные пользователем исторические метаданные Git, не измерение реальных трудозатрат. Первоначальное расписание сохрани в docs/commit-schedule.json с пометкой generated historical schedule и случайным seed.
2. Сначала составь список первоначальных коммитов N по границам работ. Первый датируй начальным днем, итоговый — конечным. Время выбирай случайно между 10:00:00 и 23:00:00 с минутами и секундами.
3. Интервал перед коммитом связывай со сложностью завершаемого изменения: небольшой config или документация — вес 1; обычная функция с тестами — 2; транзакции, анализ типов или конкурентность — 3; сложные аварийные проверки либо межпакетный анализ — 4.
4. Для N−1 интервалов умножь веса следующих коммитов на случайные коэффициенты 0.85–1.15 и нормализуй на доступный диапазон. После выбора календарных дат и времени проверь границы и строгое возрастание. При необходимости повтори генерацию. Не задавай жесткий минимум интервала: небольшое исправление может следовать в тот же день.
5. Выведи первоначальную таблицу дат и сообщений, затем продолжай без ожидания согласования. Не создавай коммиты до выполнения соответствующих работ.
6. При изменении плана перераспределяй только даты еще не созданных коммитов. Сохраняй уже записанную историю. На конечном дне оставляй запас времени для заключительных исправлений. Обновление расписания включай в очередной содержательный коммит.
7. Для каждого вызова git commit локально передавай одинаковые GIT_AUTHOR_DATE и GIT_COMMITTER_DATE в ISO 8601 с явным +03:00. Одного --date недостаточно для установки обеих дат. Имя и email используй из существующей Git identity; не выдумывай их.
8. После каждого коммита проверяй даты через git show --no-patch --pretty=fuller HEAD. В финале автоматически проверь новые коммиты в порядке родителей, а не сортировки по дате: все даты внутри диапазона, обе даты равны, каждый следующий коммит позднее предыдущего.
9. Не переписывай чужую историю и не меняй системные часы. При отсутствии Git identity сообщи о препятствии, сохрани работу и не объявляй отсутствующие коммиты созданными.

В финальном отчете покажи фактическое число новых коммитов, SHA, сообщения, AuthorDate и CommitDate.

Начинай с проверки окружения и короткого плана. Выполни реализацию и приемку, а не только подготовку файлов или рекомендаций.
